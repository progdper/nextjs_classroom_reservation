## 1. 목표와 요구사항

관리자가 등록한 강의실과 요일별 운영 시간을 기준으로, 가입한 사용자가 빈 시간을 예약하고 시작 전에 취소할 수 있는 시스템을 만든다.

| 구분     | 필요한 기능                                          |
| -------- | ---------------------------------------------------- |
| 회원가입 | 이메일·닉네임·비밀번호 입력, 이메일·닉네임 중복 방지 |
| 인증     | 사용자·관리자 공통 이메일·비밀번호 로그인, 로그아웃  |
| 관리자   | 강의실 등록, 강의실별 요일별 운영 시간·휴무 설정     |
| 예약     | 강의실·날짜·빈 시간 선택 후 즉시 확정                |
| 내 예약  | 본인 예약 목록 조회, 시작 시간 이전 취소             |
| 내 정보  | 이메일 조회, 닉네임 변경, 비밀번호 변경              |

## 2. 포함·제외 범위

이번에 포함할 내용:

- 현재 예약 간격은 1시간이며, 추후 변경하기 쉽도록 계산 기준을 한곳에서 관리한다.
- 예약 한 건은 시간대 한 개를 사용한다.
- 관리자 승인 없이 예약을 확정한다.
- 닉네임은 앞뒤 공백을 제거하고 빈 값과 중복을 허용하지 않는다.
- 가입자는 일반 사용자로 등록하고, 최초 관리자는 별도 승인된 절차로 지정한다.
- 날짜와 운영 시간은 한국 시간(Asia/Seoul) 기준으로 처리한다.
- 사용자·관리자는 동일한 로그인 화면을 사용하고 역할에 따라 메뉴와 접근 권한을 구분한다.

이번에 제외할 내용:

- 예약 변경, 반복 예약, 여러 시간대 일괄 예약
- 결제, 알림, 통계, 체크인
- 관리자에 의한 강제 예약 취소
- 이메일 변경, 비밀번호 분실 재설정, 회원 탈퇴
- 공휴일·특정 날짜의 운영 시간 예외 설정
- 자정을 넘기는 운영 시간

현재 정책은 이메일 소유 확인 없이 이메일·비밀번호로 가입하는 방식이다.
3차에서 확정한 닉네임·비밀번호 입력 규칙은 유지한다.
닉네임은 NFC 정규화·앞뒤 공백 제거 후 2~20자의 한글 완성형·영문·숫자·밑줄을 허용하며 영문 대소문자 구분 없이 중복 비교한다. 새 비밀번호는 12자 이상, 영문·숫자 포함, UTF-8 72바이트 이하로 한다. 로그인 비밀번호에는 새 비밀번호 규칙을 적용하지 않는다. 실제 Supabase 설정 변경·DB 반영은 별도 승인 대상이다.

## 3. 화면·사용 흐름

공통 메뉴:

- 강의실 예약
- 내 예약
- 내 정보
- 로그아웃
- 관리자에게만 강의실 관리 메뉴 표시

관리자도 공통 사용자 기능을 이용한다. 강의실 관리 메뉴를 선택하면 /admin/classrooms로 이동하며, 해당 화면은 src/app/admin/classrooms/page.tsx가 담당한다. 메뉴 숨김과 별개로 페이지 접근 및 변경 요청 처리 시 서버에서 관리자 권한을 검사한다.

사용자 흐름:

```text
회원가입 → 로그인 → 강의실 선택 → 날짜 선택
→ 빈 시간 선택 → 예약 요청 → 완료 → 내 예약 확인
```

```text
내 예약 → 취소 요청 → 본인 여부·시작 시각 검사
→ 취소 완료 → 해당 시간 다시 예약 가능
```

```text
내 정보 → 닉네임 변경 또는 비밀번호 변경 → 저장 결과 확인
```

관리자 흐름:

```text
공통 로그인 → 강의실 관리 메뉴 → 강의실 등록
→ 월~일 각각 운영 시간 또는 휴무 설정 → 저장
```

로딩, 빈 목록, 입력 오류, 중복 닉네임, 예약 충돌, 취소 불가 사유를 화면에 표시한다. 작은 화면과 키보드 조작, 중복 제출 방지도 확인한다.

## 4. 현재 구조와 구현 방향

### 현재 구조

Next.js App Router와 Prisma DB 연결에 사용자 인증 연결·닉네임·역할 모델 필드를 추가하였다. Supabase 인증 클라이언트·세션 Proxy·입력 검증·권한 검사와 회원가입·로그인·내 정보 화면·Server Action을 연결하였다. 강의실·예약·관리자 메뉴 연결은 후속 단계이다. 개발 DB에 최초 사용자 스키마를 반영하고 인증 설정을 확인하였다. 실제 가입·인증 계정 연결·정보 변경 검증은 미수행이다.

### 필요한 데이터

| 데이터           | 주요 내용                                            |
| ---------------- | ---------------------------------------------------- |
| 사용자           | 이메일, 고유 닉네임, 인증 계정 연결, 역할            |
| 강의실           | 이름, 위치, 생성 시각                                |
| 요일별 운영 시간 | 강의실, 요일, 운영 시작·종료 시간, 휴무 여부         |
| 예약             | 사용자, 강의실, 시작·종료 시각, 상태, 생성·취소 시각 |

인증은 Supabase Auth의 이메일·비밀번호 방식을 사용한다.
앱 User 모델은 기존 id와 name을 유지하고 authUserId, nickname,
nicknameKey, role을 추가한다. 비밀번호는 앱 테이블에 저장하지 않는다.
기존 계정을 이메일만으로 자동 연결하지 않는다.
가입·프로필 등록이 완료되지 않은 계정은 예약 기능을 이용할 수 없다.

### 서버 처리·입력 검증·권한

- 서버에서 로그인·관리자 권한·예약 소유자를 검사한다.
- 가입 요청에서 관리자 역할을 지정할 수 없도록 한다.
- 비밀번호 변경은 현재 비밀번호를 확인한 후 처리한다. 변경 후 세션 처리 정책은 인증 상세 설계에서 확인한다.
- 가입·닉네임 변경에 동일한 정규화·중복 검사 기준을 적용하고 DB 고유 제약으로 동시 요청의 중복 저장도 막는다.
- 예약 가능 시간은 해당 요일의 운영 시작 시각부터 1시간 간격으로 계산하고, 운영 종료를 넘는 시간대는 만들지 않는다.
- 예약 시작 시각은 서버의 현재 시각보다 미래여야 한다.
- 취소는 서버에서 처리하는 시각이 예약 시작 시각보다 이전인 경우만 허용한다. 시작 시각과 같거나 늦으면 거부한다.
- 취소는 삭제 대신 상태 변경으로 기록하며, 소유권·예약 상태·시각 검사를 변경 처리와 일관되게 수행한다.
- 운영 시간 변경은 변경일 이후의 기존 유효 예약과 충돌하면 거부한다.
- 시간 간격을 변경해도 기존 예약 시각은 유지하고, 기존 예약과 겹치는 새 시간대는 예약하지 못하게 한다.
- 화면에서 빈 시간으로 보이더라도 최종 저장 시 다시 검사한다. 선택만으로 시간을 선점하지 않는다.
- 다른 사용자에게는 시간의 예약 여부만 표시하고 예약자 개인정보를 제공하지 않는다.
- 특정 순간인 예약 시각은 일관된 UTC 기준으로 저장·전달하고, 한국 시간 표시와 요일 계산에는 Asia/Seoul을 명시한다.

### 화면·공통 UI

기존 App Router 구조를 유지하고 DB 연결을 재사용한다. 화면 표시, 입력 검증, 인증·권한 판정, DB 처리의 책임을 구분하되 불필요한 계층과 폴더는 만들지 않는다. 반복되는 메뉴·폼 요소만 필요에 따라 공통화한다. 동적 예약 조회의 로딩 경계와 사용자 데이터 캐시 범위를 검토한다.

## 7. 완료 기준과 검증 방법

- 이메일·닉네임 중복 가입이 거부된다.
- 닉네임 변경 시에도 중복을 허용하지 않으며 동시 요청에도 중복 저장되지 않는다.
- 비밀번호 변경 후 새 비밀번호로 로그인할 수 있고 기존 비밀번호는 거부된다.
- 사용자·관리자가 공통 로그인 화면을 사용하고 관리자에게만 강의실 관리 메뉴가 표시된다.
- 일반 사용자는 관리자 주소 직접 접근 및 변경 요청을 수행할 수 없다.
- 다른 사용자의 정보 변경·예약 취소는 서버에서 거부된다.
- 휴무일과 운영 시간 밖, 과거 시간에는 예약할 수 없다.
- 같은 강의실의 겹치는 시간에 동시 요청해도 한 건만 확정된다.
- 서로 다른 강의실의 같은 시간은 각각 예약할 수 있다.
- 본인 예약은 시작 전 취소할 수 있고, 시작 시각부터는 취소할 수 없다.
- 취소된 시간은 다시 예약할 수 있다.
- 운영 시간 변경으로 기존 예약이 무효화되지 않는다.
- 새로고침과 한국 날짜 경계에서도 결과가 유지된다.
- 처리 중·실패·빈 상태, 모바일·키보드 조작을 확인한다.

코드 적용 후 변경 파일 확인, npm run db:validate, npm run check, npm run build를 범위에 맞춰 수행한다. check는 타입·린트·서식 검사이며 실제 기능 검증을 대신하지 않는다. check·build 과정의 Prisma Client·Next.js 타입 등 자동 생성물 갱신과 실제 DB 변경을 구분한다.

실제 기능·동시성 검증은 별도 승인된 개발 DB와 테스트 계정으로 수행한다. 현재 테스트 실행 명령이 없으므로 중요한 예약·취소·권한 검증에 필요한 테스트 구성은 구현 전에 제안한다. 실행한 검사와 미검증 범위를 구분한다.

1차에서는 로컬 의존성이 없어 db:validate·check·build를 실행하지 못했다. 2차에서는 인증 패키지 설치와 인증 연결·세션 기반 코드를 적용하고 검사를 수행한다. 설치·검사에 따른 Prisma Client·Next.js 타입 등 자동 생성물 갱신은 승인 범위에 포함한다. 실제 환경 값 입력·Supabase 설정 변경·DB 접속·마이그레이션·배포는 수행하지 않는다. 검사 결과는 아래 진행 상태에 기록한다.

## 8. 승인 범위와 근거

- 확인된 요구사항: 1시간 예약 단위, 관리자 요일별 운영 시간 설정, 이메일·비밀번호 가입, 닉네임 입력·중복 불가, 내 정보의 닉네임·비밀번호 변경, 동일 로그인과 관리자 전용 메뉴.
- 작성자: 사용자가 test1로 지정함.
- 계획 파일 생성: 사용자의 “계획 파일을 생성하라.” 요청으로 승인됨. 앞서 제시한 초안과 공통 로그인·관리자 메뉴 설명을 기록함.
- 인증 연동 방향: 사용자의 “Supabase DB + Auth … 인증 연동을 진행하라.” 지시 확인.
- 구체적인 파일 변경: 1차 사용자 모델·계획 파일 diff 승인에 이어 2차 인증 연결·환경 변수 검증·세션 처리의 diff와 신규 파일 전체 내용을 제시했고, 사용자의 “진행하라” 지시로 적용 승인됨.
- 패키지 설치·환경 변수 변경: 2차에서 @supabase/supabase-js·@supabase/ssr 설치, lock 파일 및 환경 변수 예시·검증 변경 승인됨. 실제 환경 파일의 값 입력·변경은 제외.
- 스키마 수정·Client 생성: 1차 UserRole·사용자 필드 추가 승인. 2차 패키지 설치·검사에 수반되는 Client 자동 생성 승인. 실제 DB 반영은 제외.
- 실제 DB 변경·마이그레이션·데이터 쓰기: 아직 승인받지 않음.
- 배포·Git 작업: 승인 범위에 포함하지 않음.
- 계획 파일 생성 승인을 구현·DB 변경·배포 승인으로 확대 해석하지 않는다. 기록된 승인 문구만으로 새로운 권한을 부여하지 않는다.

## 10. 변경 이력과 후속 확인

- 예약 간격은 현재 1시간으로 정함.
- 운영 시간은 강의실별·요일별 설정으로 정함.
- 이메일·비밀번호 가입과 닉네임 입력을 포함함.
- 내 정보에서 닉네임·비밀번호 변경을 포함함.
- 닉네임 중복은 허용하지 않음.
- 사용자·관리자 동일 로그인과 관리자 전용 강의실 관리 메뉴를 명시함.
- 작성자 test1 및 계획 파일 생성 승인을 확인함.
- 후속 확인: 확정한 이메일 인증·비밀번호 정책의 실제 Supabase 설정, 최초 관리자 지정 방법, 실제 DB 환경과 기존 데이터, 동시성 보장 방식.
- 재개 시 이 계획과 실제 코드·미완료 변경·사용자 승인 범위를 먼저 확인한다.
- 동일 기능의 후속 작업은 이 파일을 재사용하며, 생성 후 파일명을 변경하지 않고 수정 시각·진행 상태를 갱신한다.
- Supabase DB + Auth 방식으로 인증 연동 방향을 확정함.
- 사용자 모델 변경 → 인증 연결·서버 처리 → 인증 화면·메뉴 순으로 진행함.
- 실제 DB 마이그레이션·데이터 쓰기·최초 관리자 지정은 대상 환경을 확인하고 별도 승인 후 수행함.
- 사용자 모델·계획 파일의 1차 diff에 대한 사용자의 “진행하라” 승인을 확인하고 적용함.
- authUserId·nickname·nicknameKey는 기존 데이터 영향을 줄이기 위해 선택값으로 추가함. 가입 완료 시 필수 검사·nicknameKey 정규화는 후속 서버 처리에서 구현해야 함.
- 2차 범위: 인증 패키지, 인증 환경 변수 검증, 서버 클라이언트, Proxy 세션 갱신, 설정 안내.
- 2차 변경안에 대한 사용자의 “진행하라” 승인 확인. 실제 환경 값 입력·Supabase 설정 변경·DB 마이그레이션은 제외.
- 회원가입·로그인·내 정보 화면과 역할 검사는 후속 단계. 현재 Proxy는 세션 유지 기반이며 권한 검사 자체가 아니다.
- 세션 Proxy 적용 페이지는 실행 시 인증 환경 변수가 필요하다. 조회용 클라이언트는 쿠키 변경 인증 작업에 사용하지 않으며, Server Action용 클라이언트를 구분한다.
- 2차 설치 결과: @supabase/supabase-js 2.118.0, @supabase/ssr 0.12.7. npm 설치 완료 및 설치 당시 취약점 검사 0건. Node.js v24.22.1, npm 11.19.1.
- 검증: npm run db:validate 성공, npm run check(타입·린트·서식) 성공, npm run build 성공. 최초 빌드는 제한된 네트워크에서 기존 Google Fonts 다운로드 실패, 네트워크 허용 후 동일 명령 재실행 성공. 폰트·화면 코드는 변경하지 않음.
- 검증: 실제 자격 증명 없이 Node.js·TypeScript 변환·VM 모의를 사용해 13개 항목 확인. 환경 변수 누락·잘못된 URL·HTTP·예시 값·잘못된 키의 안전한 오류, 유효 설정, 연속 쿠키 갱신·옵션 보존·요청/응답 전달·캐시 헤더, 미로그인·잘못된 세션·인증 서버 장애 분기, 조회용/Action용 쿠키 처리 확인. 임시 검증 파일은 생성하지 않음.
- 잘못된 URL 입력이 내부 URL 예외로 이어지지 않도록 인증 환경 변수 검증에 URL.canParse 검사를 추가함. DB 환경 변수 검증은 변경하지 않음.
- 모의 검증은 실제 Supabase 인증을 대신하지 않음. 실제 로그인·토큰 만료 후 갱신·로그아웃 및 외부 환경 검증은 미수행. 실제 환경 파일·Supabase 설정·DB 데이터·마이그레이션은 변경하지 않음.

- 3차 범위: 공통 인증 입력 검증과 서버 사용자·관리자 권한 검사.
- 생성 파일: src/lib/auth-validation.ts, src/lib/auth.ts. 사용자 안내: docs/SUPABASE_SETUP.md에 입력·권한 기준 추가.
