# Supabase DB 설정과 연결하기

이 안내서는 처음 Supabase를 사용하는 사람이 프로젝트 생성 → 공개 CA 인증서 저장 → 연결 주소 확인 → `.env` 등록 → 테이블 생성 순서로 진행하도록 작성했습니다. 이 문서는 로컬 개발 DB 준비와 연결을 다룹니다. 앱 설치·실행은 [시작 안내](SETUP.md), 인터넷 공개는 [Vercel 배포하기](VERCEL_DEPLOYMENT.md)를 확인하세요.

Supabase 프로젝트를 만들면 PostgreSQL 데이터베이스가 준비됩니다. 그 안에 앱에서 사용할 `users` 테이블을 만드는 작업은 뒤의 별도 단계입니다. 안내서 작성만으로 실제 DB 생성·접속·마이그레이션이 수행되지는 않습니다.

## 준비하기

- Supabase 계정과 개발·테스트용 프로젝트를 준비합니다.
- 편집기에서 보일러플레이트 프로젝트를 엽니다. 이 문서에서 **프로젝트 폴더**는 `package.json`이 있는 폴더를 뜻합니다. 복사한 폴더의 이름이나 위치는 달라도 됩니다.
- [기본 실행 안내](SETUP.md)에 따라 Node.js 24와 패키지 설치를 준비합니다.
- DB 비밀번호를 안전하게 보관할 장소를 준비합니다. Supabase 로그인 비밀번호와 DB 비밀번호는 별개입니다.

기본 첫 화면은 DB 없이 실행됩니다. 화면이 보이는 것만으로 DB 연결이 성공했다고 판단하지 마세요.

## 1. 회원가입과 Organization 생성

1. [Supabase Dashboard](https://supabase.com/dashboard)에 접속해 회원가입 또는 로그인합니다.
2. `Your organizations` 화면에 조직이 없다면 **New organization**을 누릅니다.
3. 조직 이름을 입력하고 목적에 맞는 요금제를 선택해 생성합니다. 유료 요금제나 추가 옵션을 선택할 때는 표시되는 비용을 확인하세요.
4. 이미 조직이 있다면 사용할 조직을 선택합니다.

Organization은 프로젝트를 묶어서 관리하는 공간입니다. 아직 DB 연결 주소를 입력하는 단계는 아닙니다.

## 2. 프로젝트와 데이터베이스 생성

조직에서 **New project**를 선택합니다. 화면의 명칭과 배치는 바뀔 수 있으므로 아래 항목 이름을 기준으로 찾으세요.

| 화면 항목         | 입력·선택 방법                                                                                                                                         |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Organization      | 방금 만든 조직 또는 사용할 기존 조직을 선택합니다.                                                                                                     |
| GitHub (optional) | 첫 DB 연결 확인에는 연결하지 않아도 됩니다.                                                                                                            |
| Project name      | 구분하기 쉬운 이름을 입력합니다. 예: `my-app-dev`.                                                                                                     |
| Database password | 강력한 DB 비밀번호를 정하고 안전하게 보관합니다. 두 연결 주소에 같은 DB 비밀번호를 사용합니다.                                                         |
| Region            | 앱 서버와 가까운 지역을 선택합니다. 한국에서 사용할 개발 프로젝트라면 서울 등 가까운 지역을 검토하고, Auto를 사용했다면 실제 선택된 지역을 확인하세요. |

이 보일러플레이트는 서버의 Prisma로 DB에 연결합니다. 브라우저에서 사용하는 Supabase Data API는 기본 기능에 필요하지 않습니다. **Enable Data API** 항목이 있고 Prisma만 사용할 계획이라면 끌 수 있습니다. Supabase도 [Prisma만 사용하는 경우 Data API 비활성화](https://supabase.com/docs/guides/database/prisma)를 안내합니다. 이후 Data API를 사용한다면 테이블 권한과 RLS 정책을 별도로 설계해야 합니다.

1. 입력 내용을 확인하고 **Create new project**를 누릅니다.
2. 생성이 끝날 때까지 기다립니다.
3. 프로젝트 개요에서 상태가 **Healthy**인지 확인합니다. 일시 중지된 프로젝트라면 먼저 다시 시작합니다.

프로젝트 화면에 표시되는 `https://프로젝트ID.supabase.co`는 API용 프로젝트 URL입니다. 뒤에서 `.env`에 넣을 `postgresql://` DB 연결 주소와 구분하세요.

## 3. CA 인증서 다운로드와 저장

CA 인증서는 연결 대상 서버의 인증서를 확인하는 데 사용합니다. 공개 인증서이므로 프로젝트에 포함할 수 있습니다. 비밀번호·비밀키와는 다릅니다.

### 3-1. Supabase에서 다운로드

1. 사용할 프로젝트를 엽니다.
2. 왼쪽 메뉴에서 **Database**를 선택합니다.
3. Database 메뉴의 **Settings**로 이동합니다.
4. 화면을 내려 **SSL Configuration**을 찾습니다.
5. **SSL Certificate → Download certificate**를 누릅니다.
6. 다운로드 폴더에서 파일을 확인합니다. 파일 이름은 `prod-ca-2021.crt` 등으로 표시될 수 있습니다.

인증서를 다운로드하기 위해 **Enforce SSL on incoming connections** 설정을 변경할 필요는 없습니다. 이 보일러플레이트는 연결 코드에서 TLS와 서버 인증서·호스트명 검증을 유지합니다. SSL 설명은 [Supabase 공식 연결 안내](https://supabase.com/docs/guides/database/connecting-to-postgres#ssl)를 참고하세요.

### 3-2. 프로젝트에 저장

1. Windows 파일 탐색기에서는 **파일 확장명 표시**를 켭니다. 숨겨진 확장명 때문에 `.crt.crt`가 되는 것을 방지합니다.
2. 다운로드한 파일의 이름을 정확히 **`supabase-ca.crt`**로 바꿉니다.
3. 프로젝트의 **`certs` 폴더**에 넣습니다. 이미 같은 이름의 파일이 있으면 다운로드한 공식 인증서로 교체합니다.
4. 최종 위치가 아래와 같은지 확인합니다.

```text
프로젝트 폴더/
  package.json
  .env.example
  certs/
    supabase-ca.crt
  src/
    app/
    lib/
  prisma/
```

이 저장소의 기본 위치는 `nextjs-supabase-starter/certs/supabase-ca.crt`입니다. 프로젝트를 다른 곳에 복사했다면 복사한 프로젝트의 `certs/`에 넣으세요. `docs/`나 `public/` 안에 넣지 않습니다.

기본 인증서가 이미 포함되어 있어도 사용할 Supabase 프로젝트에서 받은 공식 파일을 기준으로 확인하세요. 서로 다른 프로젝트에서 같은 CA를 사용할 수 있으므로 내용이 같을 수도 있습니다.

### 3-3. 교체할 때 알아둘 점

- 인증서 내용을 `src/lib/supabase-ca.ts`에 붙여 넣지 않습니다. 이름·만료일·지문을 코드에 따로 입력할 필요도 없습니다.
- `.env`에는 인증서 내용이나 개인 PC의 파일 경로를 넣지 않습니다. 앱과 Prisma CLI가 같은 `certs/supabase-ca.crt`를 읽습니다.
- 인증서 파일은 Git과 공유용 복사본에 포함합니다. 다운로드한 원래 이름의 파일을 프로젝트 루트에 중복으로 보관할 필요는 없습니다.
- 교체 후 개발 서버를 재시작합니다. 이미 배포한 프로젝트는 [배포할 인증서 파일](VERCEL_DEPLOYMENT.md#배포할-인증서-파일) 안내도 확인하세요.
- Windows에서는 인증서 파일을 열어 **자세히** 항목의 발급자·유효기간 등을 확인할 수 있습니다. 보기만 하면 되며, 확인을 위해 Windows의 **인증서 설치**를 할 필요는 없습니다.

## 4. 두 가지 DB 연결 주소 확인

공식 문서의 [연결 주소 확인 절차](https://supabase.com/docs/guides/database/connecting-to-postgres#get-your-connection-string)에 따라 프로젝트 상단의 **Connect**를 엽니다.

첨부 화면과 같은 `Connect to your project` 창이라면 다음 순서로 선택합니다.

1. 상단의 **Direct — Connection string** 탭을 선택합니다.
2. **Type**은 **URI**로 둡니다.
3. **Connection Method**에서 아래의 연결 방식을 각각 선택합니다.
4. 아래 **Connection string** 영역의 전체 주소를 복사합니다. 가로 스크롤로 일부만 보일 수 있으므로 복사 버튼을 사용하세요.

| 선택할 Connection Method | 일반적인 포트 | 넣을 변수      | 용도                                |
| ------------------------ | ------------- | -------------- | ----------------------------------- |
| Transaction pooler       | 6543          | `DATABASE_URL` | 앱 실행 시 읽기·쓰기                |
| Session pooler           | 5432          | `DIRECT_URL`   | IPv4 환경의 Prisma CLI·마이그레이션 |

이 안내서는 IPv4에서도 사용할 수 있는 **Session pooler**를 `DIRECT_URL`의 예시로 사용합니다. 변수 이름이 `DIRECT_URL`이어도 Session pooler 주소를 넣을 수 있습니다. IPv6로 접속할 수 있거나 IPv4 추가 옵션이 있다면 **Direct connection** 주소를 사용할 수도 있습니다. [Supabase 연결 방식 안내](https://supabase.com/docs/guides/database/connecting-to-postgres#direct-connection)

주의할 점:

- **Direct 탭 이름**과 Connection Method의 **Direct connection 선택지**는 다릅니다. Direct 탭 안에서 Transaction pooler와 Session pooler를 각각 선택하세요.
- `DIRECT_URL`에는 Transaction pooler의 6543 주소를 넣지 않습니다. 이 프로젝트는 해당 설정을 오류로 처리합니다.
- 호스트와 사용자 이름은 각 선택지에서 복사한 값을 사용합니다. 지역 이름으로 호스트를 추측하거나 포트만 임의로 바꾸지 마세요.
- **API Keys**, 프로젝트의 `https://` URL, Supabase 로그인 비밀번호는 DB 연결 주소를 대신할 수 없습니다.

## 5. 프로젝트에 `.env` 만들기

편집기의 파일 목록에서 `.env.example`을 복사해 같은 폴더에 붙여 넣고 복사본 이름을 **`.env`**로 바꿉니다. 원본 `.env.example`은 유지하세요.

```text
프로젝트 폴더/
  package.json
  .env.example  ← 비밀값 없는 예시, 그대로 유지
  .env          ← 내 실제 연결 정보, Git에 올리지 않음
  certs/
    supabase-ca.crt
```

이미 `.env`가 있다면 새로 복사해 덮어쓰지 말고 기존 내용을 확인하여 필요한 두 변수만 수정합니다. Windows에서 이름이 `.env.txt`가 되지 않도록 확장명을 확인하세요. Linux에서는 숨김 파일 표시를 켜야 보일 수 있습니다.

`.env`는 UTF-8로 저장합니다. Windows와 Linux 모두 변수명과 파일 이름의 대소문자를 이 안내와 동일하게 사용하세요.

## 6. 연결 주소와 비밀번호 입력

`.env`를 편집기에서 엽니다. 두 변수의 큰따옴표 안을 각각 복사한 실제 주소로 바꿉니다.

아래는 **형태를 설명하는 예시**입니다. `PROJECT_REF`, `POOLER_HOST`, `URL_ENCODED_PASSWORD`는 실제 값이 아니므로 그대로 사용하지 마세요.

```dotenv
# Connect에서 Transaction pooler를 선택해 복사한 주소
DATABASE_URL="postgresql://postgres.PROJECT_REF:URL_ENCODED_PASSWORD@POOLER_HOST:6543/postgres"

# Connect에서 Session pooler를 선택해 복사한 주소
DIRECT_URL="postgresql://postgres.PROJECT_REF:URL_ENCODED_PASSWORD@POOLER_HOST:5432/postgres"
```

### 6-1. `[YOUR-PASSWORD]` 교체

복사한 주소에는 `[YOUR-PASSWORD]`라는 문구가 있을 수 있습니다. 이 부분을 **프로젝트 생성 시 정한 DB 비밀번호**로 바꿉니다. 대괄호 `[`와 `]`도 함께 지웁니다. 비밀번호를 모르면 Database Settings에서 재설정할 수 있지만, 재설정하면 기존 연결에 사용한 비밀번호도 함께 갱신해야 합니다.

비밀번호에 특수문자가 있으면 **비밀번호 부분만 URL 인코딩**해야 합니다. 예를 들어 설명용 가짜 비밀번호가 `My@Pass#2026`이면 주소에는 `My%40Pass%232026`으로 넣습니다. Supabase에 설정한 비밀번호 자체를 인코딩된 문자열로 변경하는 것은 아닙니다.

| 비밀번호의 문자 | 연결 주소에 입력할 형태 |
| --------------- | ----------------------- |
| `@`             | `%40`                   |
| `#`             | `%23`                   |
| `:`             | `%3A`                   |
| `/`             | `%2F`                   |
| `?`             | `%3F`                   |
| `&`             | `%26`                   |
| `%`             | `%25`                   |
| 공백            | `%20`                   |

표는 자주 만나는 문자의 예시이며 전체 문자 목록은 아닙니다. 주소 전체를 인코딩하거나 이미 인코딩한 비밀번호를 다시 인코딩하지 마세요. 실제 비밀번호를 온라인 변환 사이트나 채팅에 입력하지 말고, 변환이 어렵다면 비밀번호를 공개하지 않는 로컬 처리 방법을 요청하세요.

### 6-2. 저장 후 확인

1. 두 변수 이름을 정확히 `DATABASE_URL`, `DIRECT_URL`로 입력했는지 확인합니다.
2. 두 주소가 `postgresql://` 또는 `postgres://`로 시작하는지 확인합니다.
3. `[YOUR-PASSWORD]`나 예시 문구가 남아 있지 않은지 확인합니다.
4. 큰따옴표가 한 쌍씩 있고, 각 주소가 한 줄에 들어 있는지 확인합니다.
5. `sslmode`, `sslaccept`, `sslcert`, `sslrootcert` 같은 TLS 옵션을 직접 덧붙이지 않습니다. 이 프로젝트가 CA 파일을 사용해 설정합니다.
6. `.env`를 저장하고 개발 서버를 재시작합니다.

Prisma CLI는 `.env.local` → `.env` 순으로 읽고 기존 프로세스 환경 변수를 우선합니다. Next.js도 자체 환경 파일 규칙으로 읽습니다. 처음에는 로컬 DB 설정을 프로젝트 루트의 `.env` 한곳에서 관리하고, `.env.local`이나 터미널에 예전 값이 있으면 중복 설정을 확인하세요. CLI는 `.env.production`·`.env.development`를 자동으로 읽지 않습니다.

실제 `.env`는 Git에서 제외됩니다. 팀원에게 공유할 때는 각자 자신의 `.env`를 만들고, 실제 주소나 비밀번호를 `.env.example`, README, 스크린샷에 남기지 않습니다.

## 7. 설정 검사와 테이블 생성

### 7-1. DB 변경 없이 스키마 검사

설치가 끝난 프로젝트 폴더의 터미널에서 실행합니다. Windows PowerShell과 Linux에서 같은 명령을 사용합니다.

```bash
npm run db:validate
```

성공하면 Prisma 스키마가 유효하다는 메시지가 표시됩니다. **이 검사는 실제 Supabase 접속·비밀번호·읽기·쓰기 성공을 확인하지 않습니다.**

### DB 변경 없이 실제 연결 점검

.env에 두 연결 주소를 입력하고 certs/supabase-ca.crt를 준비했다면 다음 명령을 실행합니다. Windows와 Linux에서 같은 명령을 사용합니다.

```bash
npm run db:check
```

- DATABASE_URL은 앱과 같은 TLS 설정을 사용해 SELECT 1을 조회합니다.
- DIRECT_URL은 설치된 Prisma CLI의 db pull --print로 DB 스키마 정보를 읽습니다. 스키마 원문은 화면에 출력하지 않고 schema.prisma에도 쓰지 않습니다. 빈 DB라서 조회할 테이블이 없어도 접속 성공으로 표시합니다.
- 공개 CA의 형식·유효기간을 확인하고 TLS 검증을 유지합니다. 연결 주소·비밀번호·DB 스키마 원문을 로그로 출력하지 않습니다.
- 두 점검 결과가 모두 성공해야 전체 성공입니다. 하나라도 실패하면 명령의 종료 코드는 1입니다. 출력되는 안내와 아래 오류 해결 항목을 확인하세요.
- 명령은 테이블·데이터·마이그레이션을 변경하지 않습니다. 실제 업무 데이터 읽기·쓰기나 마이그레이션 적용 성공을 보장하지 않습니다.

기본 설치·빌드와 선택적 GitHub Actions 예시에서는 이 명령을 자동 실행하지 않습니다. DB 연결이 필요한 경우에만 직접 실행하세요. 실행 과정에서 읽기 전용 DB 접속이 발생합니다.

### 7-2. 개발 DB에 `users` 테이블 생성

보일러플레이트의 `prisma/schema.prisma`에는 앱용 `User` 모델이 있습니다. 실제 DB의 테이블 이름은 `users`이며 `id`, `email`, `name`, `createdAt`, `updatedAt` 필드를 갖습니다. Supabase Auth의 `auth.users`와는 별개이고 로그인 기능은 포함하지 않습니다.

**다음 명령은 마이그레이션 파일을 만들고 실제 DB를 변경합니다.** 데이터가 없는 개발·테스트 DB가 대상인지 먼저 확인하세요. 기존 데이터·테이블·마이그레이션 이력이 있는 프로젝트에서는 초기 생성 명령을 그대로 실행하지 말고 현재 상태부터 확인해야 합니다. Codex가 대신 실행한다면 별도로 DB 변경을 승인해야 합니다.

처음 설정한 빈 개발 DB에 기본 모델을 적용할 때:

```bash
npm run db:migrate:dev -- --name init
```

완료 메시지를 확인한 뒤 Prisma Client를 생성합니다.

```bash
npm run db:generate
```

마이그레이션 중 shadow DB 권한 오류가 나면 중단하고 설정을 확인하세요. shadow DB는 Prisma가 변경 내용을 비교할 때 쓰는 별도 작업용 DB입니다. 필요한 경우 `.env.example`의 `SHADOW_DATABASE_URL` 안내를 참고하되, **운영 DB나 사용 중인 개발 DB를 shadow DB로 지정하지 마세요.** 오류를 피하려고 초기화·reset 명령을 실행하지 않습니다.

### 7-3. Supabase에서 생성 결과 확인

1. Supabase에서 같은 프로젝트를 엽니다.
2. **Table Editor**로 이동해 새로고침합니다.
3. **public** 스키마의 **users** 테이블이 있는지 확인합니다.
4. 기본 필드가 있는지 확인합니다. 새 테이블의 데이터가 비어 있는 것은 정상입니다.

여기까지 확인하면 CLI의 접속과 테이블 생성은 확인한 것입니다. **앱이 사용하는 `DATABASE_URL`의 읽기·쓰기는 별도로 검증해야 합니다.** 같은 테이블을 SQL Editor에서 임의로 수정하면 Prisma 이력과 어긋날 수 있습니다.

### 모델과 접근 권한

기본 User 모델은 UUID id, 고유 email, 선택 name, 생성·수정 시각을 갖습니다. Supabase의 auth.users와 별개인 앱 데이터이며 로그인·인증 사용자 연결은 직접 구현해야 합니다.

Prisma의 관리 대상은 이 프로젝트의 앱 테이블이며 Supabase의 auth·storage 스키마를 임의로 추가하지 않습니다. Prisma 연결 역할에 따라 RLS를 우회할 수 있으므로 실제 기능에서는 서버에서 사용자·소유권·역할을 검사하세요. Data API를 사용하는 테이블의 RLS·권한 정책도 별도로 확인합니다.

### 날짜·시간과 한국 시간(KST)

한국 시간 표시가 필요한 기능을 만들 때는 **저장하는 시각과 화면에 표시하는 시간대**를 구분합니다. 같은 순간이라도 UTC의 00:00은 한국 시간의 09:00으로 표시됩니다. 저장 값 자체를 9시간 뒤로 옮기는 방식으로 처리하지 않습니다.

- 생성·수정 시각처럼 특정 순간을 나타내는 값은 UTC 기준으로 일관되게 저장·전달하고, 한국 시간 표시에는 Asia/Seoul을 명시하도록 요청하세요.
- 한국 시간 기준 오늘의 목록·일별 통계는 KST 자정을 기준으로 조회해야 합니다. UTC 날짜를 그대로 잘라 쓰면 한국 날짜와 다른 결과가 나올 수 있습니다.
- 생일·영업일처럼 날짜만 필요한 값은 시각 데이터와 구분해 설계합니다.
- DB나 서버의 시간대만 바꾸면 모든 처리가 끝나는 것은 아닙니다. 표시·입력·조회 기준과 기존 데이터의 의미를 함께 확인해야 합니다.

**현재 보일러플레이트에는 구현·검증 지침만 마련되어 있습니다.** 날짜를 표시하는 화면, KST 날짜 필터·통계 기능은 아직 구현·검증하지 않았고, 기본 User 날짜 컬럼을 별도로 변경하지 않았습니다. 기능을 추가할 때 대상·화면·조회 기준을 정하고 자정 전후의 결과를 확인해야 합니다. 기존 날짜 컬럼 타입 변경이나 마이그레이션은 별도 승인 대상입니다.

Codex에는 다음처럼 요청할 수 있습니다.

> 날짜를 한국 시간으로 표시하고, 오늘의 데이터도 한국 날짜 기준으로 조회하고 싶습니다. 현재 저장 값의 의미와 날짜 컬럼 타입을 먼저 확인하고 수정안을 보여 주세요. 저장 값에 임의로 9시간을 더하거나 승인 없이 DB를 변경하지 마세요.

에이전트의 상세 구현 기준은 [DB 작업 지침](../.agent/database.md#날짜시간과-kst-처리)에 있습니다.

## 8. 로컬 앱 연결과 읽기·쓰기 확인

개발 서버를 실행합니다.

```bash
npm run dev
```

현재 보일러플레이트는 기본 첫 화면만 제공하고 DB를 조회·수정하는 화면은 없습니다. `.env`를 저장하거나 첫 화면을 열기만 해서는 앱의 DB 연결 여부를 알 수 없습니다.

앱 읽기·쓰기 검증이 필요하면 개발 DB와 확인용 데이터의 생성·조회·삭제 범위를 정해 요청하세요. 검증용 코드나 화면이 필요하면 변경안을 먼저 확인한 뒤 적용합니다. 테스트 결과는 CLI 접속·단순 연결 조회·실제 앱 데이터 읽기·쓰기를 구분해 확인하세요.

로컬 기능을 확인한 뒤 인터넷에 공개하려면 [Vercel 배포하기](VERCEL_DEPLOYMENT.md)를 따르세요.

## 로컬 DB 검증 상태

### 검증 완료

- Windows 로컬 환경에서 실제 Supabase 연결을 확인했습니다.
- `DATABASE_URL`: 앱에서 사용하는 드라이버로 `SELECT 1` 조회와 CA 인증서·호스트명 검증에 성공했습니다. TLS 1.3 연결을 사용했습니다.
- `DIRECT_URL`: Prisma 엔진의 실제 DB 접속 확인에 성공했습니다.
- 검증 과정에서 테이블·데이터·마이그레이션을 변경하지 않았습니다.

### 추가 검증 필요

- 개발 DB에 마이그레이션 적용과 테이블 생성 확인
- 앱에서 실제 데이터 읽기·쓰기

이 결과는 현재 보일러플레이트의 연결 설정을 Windows 로컬 환경에서 검증한 것입니다. 다른 프로젝트에서 사용하거나 연결 정보·인증서를 변경하면 다시 확인해야 합니다. Linux의 실제 DB 연결은 아직 검증하지 않았습니다. 배포 환경의 검증 범위는 [Vercel 배포 검증 상태](VERCEL_DEPLOYMENT.md#현재-배포-검증-상태)를 확인하세요.

## 완료 확인표

- [ ] 사용할 개발·테스트 프로젝트가 준비되어 있습니다.
- [ ] 해당 프로젝트의 공식 CA가 `certs/supabase-ca.crt`에 있습니다.
- [ ] 프로젝트 루트의 `.env`에 두 연결 주소와 올바른 DB 비밀번호를 설정했습니다.
- [ ] `npm run db:validate`로 스키마 문법을 확인했습니다.
- [ ] 필요한 경우 승인된 개발 DB에 마이그레이션을 적용하고 `public.users`를 확인했습니다.
- [ ] 별도 검증 코드로 로컬 앱의 읽기·쓰기를 확인했습니다.

이 확인표는 보일러플레이트를 사용하는 각 프로젝트에서 확인할 항목이므로 빈 상태로 제공합니다. 해당 프로젝트에서 실제로 수행한 항목에만 체크하세요. 위의 로컬 연결 검증 결과가 새 프로젝트의 설정이나 마이그레이션·실제 데이터 읽기·쓰기 성공을 보장하지는 않습니다.

## 앱 회원 인증 연결

Supabase Auth는 PostgreSQL 연결과 별도로 설정합니다.
`.env.example`의 `NEXT_PUBLIC_SUPABASE_URL`과
`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`를 실제 환경 파일에 추가하세요.
기존 `DATABASE_URL`·`DIRECT_URL`과 같은 Supabase 프로젝트를 사용합니다.

인증용 키에는 publishable key를 사용합니다.
DB 비밀번호와 secret key는 공개 환경 변수에 넣지 않습니다.
설정 후 개발 서버를 재시작하세요.

Proxy가 적용된 페이지는 실행 시 인증 설정이 필요합니다.
인증 설정은 함수 호출 시 검증하므로 모듈을 불러오는 시점에는
실제 연결 정보가 필요하지 않습니다.

회원가입(`/signup`)·로그인(`/login`)·내 정보(`/account`) 화면과 서버 처리가 연결되어 있습니다.
로그인 전에는 로그인·회원가입 메뉴를, 로그인 후에는 내 정보·로그아웃 메뉴를 표시합니다.
이 MVP는 이메일 소유 확인을 생략하고 이메일·비밀번호로 가입합니다.
Supabase의 Confirm email을 비활성화해야 하며,
코드 수정만으로 실제 Supabase 설정이 변경되지는 않습니다.
가입 인증 메일·이메일 인증 콜백·이를 위한 SMTP 설정은 사용하지 않습니다.

### 회원 입력·권한 기준

- 닉네임은 2~20자의 한글 완성형·영문·숫자·밑줄을 사용합니다.
- 앞뒤 공백과 문자 정규화를 적용하고 영문 대소문자 구분 없이 중복을 검사합니다.
- 새 비밀번호는 12자 이상, 영문·숫자 포함, UTF-8 72바이트 이하입니다.
- 로그인에는 새 비밀번호 생성 규칙을 적용하지 않습니다.
- 로그인·앱 사용자 정보 등록을 완료해야 예약할 수 있습니다.
- 관리자 권한은 앱 User 테이블의 role을 기준으로 검사합니다.
- 입력한 이메일의 실제 소유 여부는 확인하지 않습니다.
- 실제 Supabase 설정 변경과 DB 반영은 대상 환경을 확인한 후 수행합니다.

### 가입·사용자 정보 변경

가입 전에 앱 사용자 모델이 개발 DB에 반영되어 있어야 합니다. 스키마 파일을 수정하거나 빌드한 것만으로 실제 DB 테이블이 바뀌지는 않습니다.

1. 인증 환경 변수를 설정하고 Supabase의 Confirm email을 비활성화합니다. 설정이 켜져 있어 가입 세션이 반환되지 않으면 즉시 가입 설정을 확인하도록 안내합니다.
2. `/signup`에서 이메일·닉네임·비밀번호를 입력합니다. 가입 성공 후 내 정보로 이동합니다.
3. 닉네임 사전 검사는 시간을 선점하지 않습니다. 최종 저장 시 DB 고유 제약으로 중복을 막습니다.
4. 인증 계정은 생성되었지만 앱 사용자 정보가 저장되지 않았다면, 로그인 후 내 정보에서 닉네임을 저장하여 등록을 마칩니다. 같은 이메일의 기존 앱 사용자와 자동 연결하지 않습니다.

3. 예약 가능한 시간 한 개를 선택하고 **예약하기**를 누릅니다. 선택만으로 예약되지는 않으며, 서버가 최종 상태를 확인한 뒤 즉시 확정합니다. **최신 시간 확인**으로 현황을 다시 조회할 수 있습니다.
4. **내 예약**의 **예정·이용 중**에서 예약을 확인합니다. 시작 전 본인 예약에만 **예약 취소** 버튼이 표시되며, 제출 시 서버에서 다시 검사합니다.
5. 취소 성공 후 **지난 예약·취소 이력**으로 이동합니다. 지난 예약과 취소 기록은 삭제하지 않고 표시합니다. 내 예약 목록은 페이지당 20개입니다.

휴무·예약 가능한 시간이 없는 경우, 빈 목록, 입력·조회·저장 오류와 처리 중 상태를 표시합니다. 예약 또는 취소 응답을 받지 못한 경우에는 중복 요청 전에 내 예약의 실제 상태를 확인하도록 안내합니다.

화면 검증에서는 기존 로그인 세션으로 휴무일 안내, 운영일의 1시간 간격 시간대, 시간 선택 후 버튼 활성화, 내 예약·이력 빈 목록과 메뉴 이동을 확인했습니다. 미로그인 상태의 두 페이지 접근은 로그인으로 이동했습니다. 예약·취소 제출은 수행하지 않았으므로 성공·충돌·취소된 실제 예약 행의 화면 확인은 후속 실제 저장 검증 대상입니다. 한국 시간의 연말·자정 표시는 모의 테스트로 확인했습니다.

### 실제 예약·취소 검증 결과

2026-10-27 KST에 승인된 개발 환경에서 기존 로그인 관리자 계정으로 검증했습니다. 대상은 `검증용 강의실 20261027`의 2026-11-02 10:00~11:00(KST)이었습니다.

1. 첫 예약을 생성하고 완료 안내와 내 예약의 예약 예정 표시를 확인했습니다.
2. 다른 탭에 남아 있던 이전 현황으로 같은 시간을 예약 요청했을 때 서버가 이미 예약된 시간으로 거부했습니다. 실제 동시 요청 검증과는 구분합니다.
3. 시작 전 취소 후 이력의 취소됨 표시와 시간대 재개방을 확인했습니다.
4. 같은 시간으로 다시 예약하고 두 번째 예약도 취소했습니다.
5. 최종 DB 읽기 확인에서 해당 예약 기록 정확히 2건·모두 CANCELLED·취소 시각 존재 및 시작 전 취소, 전체 확정 예약 0건을 확인했습니다. 회원·강의실·운영 시간 건수와 대상 운영 시간은 유지됐고, 새 브라우저 오류는 없었습니다.

테스트 예약은 삭제하지 않고 취소 이력 두 건으로 보관합니다. 기존 사용자 정보·강의실·운영 시간·인증 설정은 변경하지 않았습니다. 위 기록은 관리자 계정의 예약 흐름 검증 당시 상태입니다. 일반 사용자 권한과 동시 처리의 후속 결과는 아래 기록을 참고하세요. 이 두 항목의 후속 DB 트랜잭션 검증 결과도 아래에 기록했습니다. 해당 분기의 모의 테스트·읽기 전용 SQL 검증과 실제 사용자 동작 검증을 구분합니다.

### 일반 사용자 권한·동시 예약 통합 검증

2026-10-27 KST에 사용자 승인으로 기존 테스트 계정 A·B의 비밀번호를 Supabase 공식 관리자 API로 각각 무작위 값으로 변경하고, 새 비밀번호 로그인 및 인증 사용자 ID 연결을 확인했습니다. 기존 개발 프로젝트의 관리자용 키를 일시적으로 사용했으며 새 키 생성·환경 변수 추가는 하지 않았습니다. 키 전달용 Git 제외 임시 파일은 사용 직후 삭제했고, 비밀번호·토큰은 문서나 파일에 저장하지 않았으며 검증 후 테스트 세션을 로그아웃했습니다. 기존 관리자 계정의 비밀번호·회원 프로필·역할은 변경하지 않았습니다.

두 일반 사용자 세션으로 기존 인증·권한·예약 코드를 실행하는 서버 통합 검증을 수행했습니다. Supabase Auth의 사용자 확인과 Prisma DB 연결·트랜잭션·행 잠금은 실제 서비스를 사용했습니다. Next.js의 요청 쿠키 어댑터는 로그인한 테스트 SDK 클라이언트로 연결하고, 리다이렉트/권한 거부 및 캐시 갱신의 프레임워크 부분은 검증용 어댑터를 사용했습니다. 브라우저에서 동시에 클릭하거나 전체 HTTP Server Action 경로를 실행한 검증과는 구분합니다.

- 두 트랜잭션이 같은 강의실 잠금 지점에 모두 도달한 뒤 동시에 실제 잠금을 시도하도록 맞췄습니다. 하나만 예약에 성공하고 다른 하나는 중복으로 거부됐으며, DB 확정 예약은 정확히 한 건이었습니다.
- 다른 계정의 내 예약 목록에는 해당 예약이 나타나지 않았습니다.
- 다른 계정이 실제 예약 ID와 위조한 예약자 ID를 보내 취소를 시도해도 거부됐고, 원래 예약과 소유자가 유지됐습니다.
- 두 일반 계정 모두 관리자 강의실 저장 처리에서 권한 거부됐습니다.
- 예약한 계정의 정상 취소는 성공했습니다. 이번 검증에서 생성한 한 건은 취소 이력으로 남겼습니다.

최종 DB 상태는 확정 예약 0건·취소 이력 3건입니다. 앞선 관리자 테스트의 취소 이력 두 건에 이번 한 건이 추가됐습니다. 회원 3명·관리자 1명·강의실 1개·기존 월요일 운영 시간은 유지됐습니다. 시작 시각 이후 취소 거부와 운영 시간 변경 충돌의 후속 롤백 검증 결과는 아래를 참고하세요. 브라우저 두 사용자 세션의 전체 HTTP 동시 요청도 아래 후속 검증에서 확인했습니다. 앱 내 비밀번호 변경 화면의 기존 실제 미검증 상태는 관리자 API를 통한 비밀번호 재설정과 구분합니다.

### 시간 경계·운영 시간 변경 롤백 검증

2026-10-27 KST에 승인된 개발 DB에서 검증용 예약 세 건을 각각 별도 트랜잭션 안에만 생성하고, 업무 처리 확인 후 모두 롤백했습니다. 계정 비밀번호·관리자 키는 사용하거나 변경하지 않았습니다.

| 사례                                                  | 확인 결과                              |
| ----------------------------------------------------- | -------------------------------------- |
| DB 현재 시각을 기준으로 막 시작한 예약 취소           | 거부, 확정 상태·취소 시각 없음 유지    |
| 이미 종료한 예약 취소                                 | 거부, 기존 예약 내용 유지              |
| 미래 예약이 있는 요일을 휴무로 변경                   | 거부, 강의실·운영 시간 유지            |
| 운영 시작을 예약 시작보다 늦게 변경                   | 거부, 강의실·운영 시간 유지            |
| 운영 종료를 예약 종료보다 이르게 변경                 | 거부, 강의실·운영 시간 유지            |
| 운영 시간을 예약의 시작·종료와 정확히 일치하도록 변경 | 허용, 예약 시각·상태 유지 후 전체 롤백 |

기존 예약·취소·강의실 저장 코드, 실제 Prisma 연결·SQL·행 잠금·DB 현재 시각을 사용했습니다. 인증 사용자는 검증용 어댑터에서 지정하고 Next.js 화면 갱신도 어댑터로 처리했습니다. 각 Action의 내부 트랜잭션은 검증용 바깥 트랜잭션에 연결했으므로 독립 커밋이나 브라우저 전체 HTTP 검증을 의미하지 않습니다. 정확히 같은 시작 시각의 취소 거부는 기존 모의 테스트에서 확인했고, 이번 실제 DB 검증은 시작 직후와 종료 후를 확인했습니다.

세 건의 테스트 예약이 남지 않았으며, 검증 전후 사용자·강의실·운영 시간·예약 데이터 전체를 비교해 동일함을 확인했습니다. 최종 상태는 회원 3명·강의실 1개·운영 시간 1개·기존 취소 이력 3건·확정 예약 0건입니다. 미래 예약에 대한 일시적 운영 시간 변경도 롤백되어 월요일 10:00~17:00 운영이 유지됩니다.

### 브라우저 전체 HTTP 동시 예약 검증

2026-10-27 KST에 승인된 개발 환경에서 일반 테스트 계정 A·B로 전체 브라우저 요청 경로를 확인했습니다. 비밀번호를 공식 관리자 API로 다시 무작위 설정하고 실제 로그인 화면에서 로그인했습니다. 관리자용 키와 로그인 전달용 임시 파일은 사용 직후 삭제했으며 계정·비밀번호·토큰 원문을 기록하지 않았습니다.

- `qa-a.localhost`·`qa-b.localhost`의 서로 다른 호스트 전용 쿠키로 두 로그인 세션을 분리했습니다. 기존 `127.0.0.1` 관리자 세션은 유지했습니다.
- 임시 HTTP 중계 서버를 `127.0.0.1:3100`에만 열었습니다. 실제 브라우저의 두 예약 POST를 모두 받은 뒤 기존 앱 서버로 함께 전달했습니다. 요청 본문·쿠키·토큰은 로그에 남기지 않았습니다.
- 대상은 기존 검증용 강의실의 2026-11-02 10:00~11:00(KST)이었습니다. 두 요청이 모두 도착한 뒤 약 0.22ms 간격으로 전달됐고, 어느 응답도 완료되기 전에 두 요청 모두 전달된 것을 시각 기록으로 확인했습니다.
- 로그인 쿠키·Proxy·실제 Server Action·인증/권한·Prisma 트랜잭션·DB 잠금·응답·화면 갱신을 실제 앱으로 실행했습니다. 프레임워크·인증·DB 대역은 사용하지 않았습니다.
- 한 브라우저에는 예약 완료, 다른 브라우저에는 이미 예약된 시간 안내가 표시됐습니다. 두 HTTP 응답은 Server Action 응답으로 모두 200이었고 업무 결과는 각각 성공·중복 거부였습니다.
- DB 확정 예약은 정확히 한 건이었고, 실패한 사용자의 내 예약은 비어 있었습니다. 성공한 사용자의 내 예약에는 예약 예정과 취소 버튼이 표시됐습니다.
- 성공한 사용자가 브라우저에서 정상 취소했고 이력의 취소됨 표시까지 확인했습니다. 새 브라우저 오류는 두 세션 모두 없었습니다.

최종 상태는 확정 예약 0건·취소 이력 4건입니다. 기존 세 건에 이번 한 건의 이력이 추가됐습니다. 회원 3명·관리자 1명·강의실 1개·월요일 10:00~17:00 운영과 기존 관리자 로그인은 유지됐습니다. 두 테스트 세션을 로그아웃하고 검증 탭·임시 중계 서버를 종료했으며 임시 비밀 파일이 남지 않았음을 확인했습니다. 앱 소스·환경 변수·패키지·DB 스키마·마이그레이션은 변경하지 않았습니다.

이 검증은 로컬 개발 서버에서 수행한 것으로, 배포 환경의 HTTPS·쿠키·도메인·프록시 구성 검증을 대신하지 않습니다. 앱 내 비밀번호 변경 화면의 실제 검증은 여전히 별도 항목입니다.
