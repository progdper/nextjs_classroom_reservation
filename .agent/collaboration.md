# 비개발자 협업 지원

GitHub 협업, 브랜치, 팀 변경 반영, 파일 이동·이름 변경, 충돌 해결, PR·병합 작업에 적용한다.
공통 승인 규칙과 작업 흐름은 [AGENTS.md](../AGENTS.md)를 따른다.

사용자에게 Git 명령이나 충돌 해결 절차를 외우도록 요구하지 않는다.
사용자가 원하는 작업을 설명하면 Codex가 필요한 확인과 절차를 안내한다.

## 작업 시작

- 현재 브랜치, 미완료 변경과 원격 저장소 연결 상태를 확인한다.
- 팀의 최신 변경 확인이나 작업 브랜치 준비가 필요하면 이유와
  실행할 작업을 쉬운 말로 설명한다.
- 로컬 작업을 보호하고 공통 승인 규칙에 따라 진행한다.

## 개발 중

- 불필요한 파일 이동·이름 변경을 피한다.
- 다른 팀원의 변경을 임의로 덮어쓰거나 버리지 않는다.
- 파일 이동이 필요하면 관련 import와 참조 경로를 함께 확인한다.

## 팀 작업에 반영하기 전

- 변경 내용을 요약하고 가능한 타입·린트·빌드 검사를 수행한다.
- 팀 변경과 겹치는 부분이 있으면 양쪽 의도를 확인하고
  함께 유지할 수 있는 수정안을 제시한다.
- 판단이 필요한 부분은 기술 용어 대신 기능과 사용자 영향을 설명한다.
- 충돌 표시가 사라진 것만으로 정상 동작한다고 판단하지 않는다.
- 실제 검사 결과와 확인하지 못한 부분을 구분해 알린다.
- commit·push·merge 등은 공통 승인 규칙을 따른다.

## 계획 파일 협업

- plans/는 사용자와 팀원이 공유하는 기능별 계획이다. 작업 시작 전 관련 계획과 현재 브랜치·코드 변경을 함께 확인한다.
- 생성 시각·작성자·작업명을 포함한 파일명으로 새 파일의 충돌을 줄인다. 정확한 형식과 작성자 확인 순서는 [계획 작성 안내](../plans/README.md#파일-이름과-작성자)를 따른다.
- Git user.name은 GitHub 사용자명과 같다고 가정하지 않는다. 원 제작자·저장소 소유자·기존 커밋 작성자도 현재 요청자로 임의 사용하지 않는다.
- 이름이 겹치면 기존 계획을 덮어쓰지 않는다. 같은 기능의 후속 작업은 기존 계획을 확인하고, 별도 작업에만 새 파일을 만든다.
- 고유한 파일명도 동일 파일의 동시 수정 충돌을 방지하지 못한다. 충돌 시 양쪽 요구사항·승인 근거·실제 수행 결과를 대조하고 판단이 필요하면 사용자에게 확인한다.
- 계획 파일의 수정·공유와 Git commit·push·merge 승인은 구분한다. 비밀값은 기록하지 않고, 검증하지 않은 작업을 완료로 합치지 않는다.

## 사용자 안내

사용자는 원하는 기능과 결과를 설명하면 된다.
브랜치 관리나 충돌 처리가 필요하면 Codex가 먼저 안내한다.
진행 상황은 “확인 중”, “수정안 준비”, “검사 완료”처럼
쉬운 말로 설명하고, 필요한 결정만 사용자에게 요청한다.
